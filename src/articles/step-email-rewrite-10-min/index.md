# ステップメールを 18 通から 6 通に書き直した ── 自動化が動き始めた日に、本当の仕事が始まる

## 第一部　自動化が動き始めた日に気づいた違和感

### 1. 何を作っていたかの再確認

前作「APIの届かない場所を、AIが埋めた」で、自社で運用しているある適性診断 SaaS のメールファネルを、Brevo で隅々まで自動化した話を書きました。

コンタクトリストとカスタム属性、18 通のメールテンプレートを TypeScript スクリプトで API から作成し、API がないオートメーションワークフローの構築は Claude Cowork と Claude in Chrome に任せた。

Brevo の管理画面を直接開いた回数はゼロ、というのが結論でした。

今回はその続きの話です。

そのサービスは、エンジニア向けに自己診断を提供するセルフ・アセスメント SaaS で、資質・特性・経験の 3 種類の診断を無料で提供し、診断後に 980 円のプレミアムレポート(15 枚程度の詳細レポート)を販売しています。

前作で組んだのは、診断完了をトリガーに 30 日間で 6 通のフォローアップメールを段階配信するファネルでした。

3 診断それぞれに 6 通用意していたので、メールテンプレートは合計 18 通。Brevo のオートメーションワークフローも 3 本走らせていました。

今回扱うのは、これを「診断の種類を問わない 1 本の 6 通シーケンス」にまとめ直した、その後の話です。

### 2. テストメールを読み返して気づいた、4 つの問題

ファネルが動き始めて数日後、配信されてくる自分宛のテストメールを読み返していて、気づきました。自動化は組み上がったが、中身が間違っていた。

CEO 一人称の説教調、バックエンド寄りの比喩、自己理解という抽象を提示しただけで、実際に案件を取るという目的につながっていないコンテンツ。3 診断を順に受けた受診者に同型のメールが 3 度届く重複配信。

受診者の身になって読み返すと、これは送るに値しないメールでした。

問題は 4 つありました。

1 つ目は、CEO 一人称の説教調です。「あなたというコンポーネント」「ADR を書かないエンジニアは設計の責任を取れない」のような、書きたいことだけを書いたメールが並んでいました。

受診者はこのサービスに辿り着いたエンジニアです。知人の知人に向かって書く文体ではなく、同じ立場の人として書く文体であるべきでした。

2 つ目は、比喩がバックエンドに偏っていたことです。次のような語彙は、フロントエンド・モバイル・データ・若手のエンジニアを排他しかねません。

- コンポーネント
- ADR
- git diff
- マージ

職種横断的な言葉でいい場所にまで、無自覚に技術固有名詞を入れていました。

3 つ目は、受診者の関心とのズレです。受診者が主に気にしているのは、次のあたりです。

- 案件・プロジェクト獲得率の向上
- 単価交渉
- スカウト返信率の改善
- 面談通過率の改善

一方、書いていたメールは、自己の理解を深めることだけに集中していました。診断結果を眺めて自分を理解する、という終着点で止まっていて、実際に案件を取る場面で活かせていなかったのです。

4 つ目は、重複配信です。3 診断を順に受診した受診者には、ほぼ同型の Step3(プレミアムレポートのおすすめ)と Step6(再診断のお知らせ)が 3 度届きます。

本文の 8 割が共通という代物で、3 通目を読む頃には間違いなく配信解除される構成でした。

これらの問題は、前作の自動化を組み上げる時には見えていませんでした。ファネルが動いたことに満足していて、配信されているメールの中身を真面目に読んでいなかったのです。

## 第二部　Deep Research で診断し、書き直す

### 3. 業界の一次・二次ソースを要件定義書に落とす

直観で書き直すこともできましたが、それでは再現性がありません。「説教調を直そう」と感覚で書き直すのと、業界ベンチマークと定量の基準を引きながら書き直すのとでは、結果も、引き継ぎやすさも違います。

そこで Claude Deep Research と Gemini Deep Research を併用し、業界の一次・二次ソースを当たりました。

調査範囲は次のとおりです。

- フリーランスエンジニアの案件獲得経路(フリーランス白書 2024、ランサーズフリーランス実態調査 2024)
- IT エンジニアの単価ベンチマーク(HiPro Tech IT フリーランスエンジニア平均月額単価ランキング 2024、PE-BANK 単価交渉術)
- スカウト返信率の改善 Tips(Findy、LAPRAS のカジュアル面談調査)
- ステップメールの開封率・CTR・配信解除率の業界ベンチマーク(Mailchimp、SendGrid、Plezi 等の集計)
- Apple Mail Privacy Protection によって開封率が 10–30% 過大計上される caveat

両方の Deep Research の出力をマージし、自分の主観評価と合わせて、要件定義書を 1 本書きました。リポジトリの `docs/email-redesign-requirements.md` です。

180 行ほどのドキュメントで、現状の課題、設計目的、5 つの設計原則、推奨シーケンス、パーソナライズ設計、KPI ベンチマーク、避けるべき表現、出典までを含めています。

### 4. 5 つの設計原則と KPI ベンチマーク

5 つの設計原則のうち、特に効いたのは次の 3 つでした。

1 つ目は、自己理解は手段で、案件を取ることが目的、という考え方です。

各通の前半で、受診者が日々ぶつかる業務課題(応募・面談・単価)を持ち出し、後半で、その課題に当てはまる形で診断結果を示す。比率は前段ほど課題寄り、後段ほど診断結果寄り、という配分で固定しました。

2 つ目は、比喩の密度を下げることです。1 通あたり技術比喩 2 個以下、技術固有名詞 5 個以下、というルールを置きました。具体的にはこういう置換です。

- コンポーネント → 成果物
- ADR → 意思決定の記録
- git diff → 差分
- マージ → 統合

このように、職種を問わず通じる言葉に置き換えていきました。

3 つ目は、最初の 1 週間に配信を集中させることです。登録直後のメールは開封率が高いので、その期間を活かすために最初の 1 週間に 3 通を集中して置きました。

0 日目、2 日目、5 日目、10 日目、17 日目、28 日目の 6 通という、等間隔ではなく前半に寄せたスケジュールに直しています。

KPI ベンチマークも、要件定義書に組み込みました。Apple MPP の影響を踏まえ、開封率は到達率の目安としてだけ参照する。

主指標は CTR / CTOR と購入転換率に置く。配信解除率は 0.5% を超えたらすぐ見直す、というラインを引いておきました。

これは後でメール文面を A/B 検証するときに、判断のものさしになります。

### 5. 6 通を前半に集中させたスケジュールへの再設計

旧構成と新構成の違いはこうです。

| 旧                         | 新                                      |
| -------------------------- | --------------------------------------- |
| 3 funnel × 6 通 = 18 通    | 1 funnel × 6 通                         |
| 完了リスト 3 本がトリガー  | `Onboarding_Active` 単一トリガー        |
| 等間隔(30 日 6 通)         | 0,2,5,10,17,28 日目(前半に集中)         |
| 件名・本文を診断ごとに作る | 70% 共通 / 30% `LATEST_TYPE` で差し込み |
| 重複配信あり               | `Do not re-enter` で 1 度のみ           |

70% / 30% の根拠はこうです。6 セクション構成のうち、次の 5 セクションを共通化します。

- 件名
- 冒頭のつかみ
- 課題の提示
- 次にしてほしい一手
- 行動喚起の基本部分

「診断結果の翻訳ブロック」だけを `LATEST_TYPE` で分岐させると、ちょうど共通 7 割・差し込み 3 割になります。差し込みは Brevo Liquid の `{% if %}` で表現します。

資質診断・特性診断・経験診断のそれぞれで、同じ「自己紹介 3 行テンプレ」を作るときの作り方の例だけを差し替える。骨格は全員共通です。

新しいトリガーリストとして `Onboarding_Active` を 1 本作り、アプリ側で「いずれかの診断完了時に、このリストに 1 度だけ追加する」という統合エントリーポイントに変えました。

既存の `Aptitude_Completed` 等の 3 リストは分析・セグメント用に残しています。

Exit Condition は前作と同じ `Premium_Purchased` への加入、Do not re-enter を有効化、というシンプルな構成です。

## 第三部　コンテンツの IaC 化と、人が手を動かしたのは 10 分

### 6. Markdown 正本と、ビルドパイプライン

旧構成では、メール文面は HTML を直接編集していました。これは前作の自動化を組んだときの、いわば負債です。

HTML の差分は git diff で読むのが辛い。`<table>` のネストや `style` 属性のインライン記述に紛れて、文章としての変更点が見えなくなる。

レビューが目で追いにくく、PR で議論しにくい状態でした。

今回の再設計を機に、メール文面を Markdown で書く構成に切り替えました。

- `.md` が正本(人間がレビューする原稿)
- `.html` は `npm run build:emails` で `.md` から自動生成された成果物
- `.html` を直接編集しないルール

このパイプラインは `src/build-emails.ts` として実装しました。387 行ほどの TypeScript で、frontmatter のパース、Markdown→HTML 変換、独自ブロック記法の解釈、Liquid 変数の温存、を担います。

独自ブロック記法は 3 種類用意しました。Markdown の `:::` 拡張記法を使い、メールテンプレートで頻出するパーツを宣言的に書けるようにしています。

```markdown
::: highlight
あなたの最新診断: {{ contact.LATEST_TYPE }}
タグ: {{ contact.ASSESSMENT_TAGS }}
:::

::: cta href="https://example.com/result"
診断結果の詳細を確認する
:::

::: signature
サービス運営チーム
:::
```

`::: highlight` は薄紫背景のボックス、`::: cta` は中央配置のボタン、`::: signature` は署名ブロックに、それぞれビルド時に展開されます。

肝心なのは、Liquid 変数 `{{ contact.LATEST_TYPE | default: "サービス" }}` のような Brevo 側で展開される変数を、ビルドプロセスで壊さずに通す処理です。Markdown のエスケープ規則にぶつかると `{{` が `&#123;&#123;` に化けます。

`build-emails.ts` の中で Liquid 構文を一旦プレースホルダに退避し、HTML 化が済んでから戻す、という単純な手当てを入れています。

frontmatter には件名・preheader・タグ(Brevo テンプレート ID を割り振るための識別子)を置きます。本文の中に件名や preheader を埋めない、という分離です。

```markdown
---
tag: assessment-unified-step1-welcome
subject: 診断結果と、明日からの案件応募で使う3行
preheader: 診断結果から自己紹介3行を作って、今日から提案資料に貼ってください。
---

{{ contact.FIRSTNAME | default: "エンジニア" }} さん

診断、お疲れさまでした。
(以下本文)
```

結果として、メール文面の修正は「PR でレビューできる差分」になりました。

`step1_welcome.md` を編集し、`npm run build:emails` を走らせ、生成された HTML が想定どおりかをローカルで確認し、`npm run register` で Brevo にアップロードする。

インフラを Terraform で管理するときの `plan → apply` の感覚に近い動線です。

### 7. 役割分担と、10 分の内訳

冒頭で「画面を直接操作した時間はおよそ 10 分」と書きました。誇張ではないことを、工程ごとの責務分担表で示します。

| 工程                                                 | 担当                          | 人間の介在                     |
| ---------------------------------------------------- | ----------------------------- | ------------------------------ |
| Deep Research(要件定義書の起草)                      | Claude(Deep Research モード)  | 質問入力と最終承認のみ(〜2 分) |
| 6 通の Markdown 原稿執筆                             | Claude Code                   | PR レビュー(〜3 分)            |
| `build-emails.ts` の実装と HTML 生成                 | Claude Code                   | コマンド実行確認のみ           |
| 旧 18 通テンプレートの Brevo からの削除              | Claude Code(API)              | なし(冪等スクリプト)           |
| 新 6 通テンプレートの Brevo への登録・有効化         | Claude Code(API)              | なし                           |
| 新リスト `Onboarding_Active` の作成                  | Claude Code(API)              | なし                           |
| Brevo オートメーションワークフローの再構築(管理画面) | Cowork + Claude in Chrome     | 1 箇所の UI 確認(〜3 分)       |
| 動作確認のテスト送信                                 | Claude Code(API でテスト送信) | 受信メールの目視(〜2 分)       |

合計で、直接手を動かしたのはおよそ 10 分です。

なぜ 10 分で済んだのか、理由は 4 つあります。

役割分担が明確だったから、というのが第一の理由です。3 つの担当の境界をこう固定しています。

- Claude Code: コードと API
- Cowork: ブラウザと管理画面
- Deep Research: 未知の領域の調査

境界が固定されているので、どのタスクをどちらに振るかで悩む時間がほぼゼロでした。

指示書をコードのように書いたから、というのが第二の理由です。Cowork に渡す Brevo オートメーション再構築の指示書 `docs/automation-workflow-setup.md` は、Claude Code に書かせました。

テンプレート ID(156–161)、各ステップの遅延日数(D+0/2/5/10/17/28)、条件分岐(`Premium_Purchased` に含まれるか)、Exit Condition、Do not re-enter フラグの ON/OFF まで、全て一意に明示されています。

Cowork が「行間を読む」必要がない指示書です。これは前作で得た最大の学びでした。

API スクリプトが冪等だったから、というのが第三の理由です。`npm run register` は、テンプレート名・タグで既存リソースを検出し、存在すれば UPDATE に切り替えます。`npm run activate-templates` も既に有効なテンプレートをスキップします。

再実行で壊れません。「とりあえず流して、結果を見て、また流す」が成立する設計になっているので、人間が「これ流して大丈夫か」と心配する時間がありません。

Markdown 正本がレビュー可能だったから、というのが第四の理由です。HTML を直接編集していた頃は、PR の差分が読めず、文面の変更点を確認するためにブラウザでプレビューを開く必要がありました。

Markdown 正本になったことで、git diff だけで何が変わったかが分かります。レビュー時間が大きく短くなります。

10 分の内訳をきっちり数えると、こうなります。

- 要件定義書の最終承認: 2 分
- Markdown 6 通の PR レビュー: 3 分
- Cowork が Brevo オートメーションを構築している途中、テンプレート選択 UI の挙動を 1 箇所だけ目視確認: 3 分
- 受信したテストメールの目視: 2 分

10 分のうち、9 分は「判断」と「目視」です。タイピングは事実上ゼロでした。

Cowork が 1 箇所だけテンプレート選択 UI で迷ったときに、画面を覗き込んで「Use a template の方を選んで」と指示した、という程度の介入です。

これは、自動化が「コードを書かなくていい」段階から「キーボードに触らなくていい」段階に進んだことを意味します。残った 10 分は、人間が判断するためだけに残された時間です。

### 8. 書き直したメールの中身

新しい 6 通のテーマ表は次のとおりです。

| Step | 配信日 | 主題                                            |
| ---- | ------ | ----------------------------------------------- |
| 1    | D+0    | 自己紹介 3 行テンプレ(そのまま提案資料に貼れる) |
| 2    | D+2    | 単価交渉の根拠を 3 点に整理する                 |
| 3    | D+5    | スカウト返信率を上げる 5 行テンプレ             |
| 4    | D+10   | 面談でよく訊かれる 5 つの質問への答えを揃える   |
| 5    | D+17   | 落ちた案件を自分でふり返る                      |
| 6    | D+28   | リピートや紹介を取りに行くための型を言葉にする  |

「自己理解」というテーマが、各通でその日に使える具体的な部品(テンプレ・チェックリスト・問いかけの型)に置き換えてある点を見てください。

Step 1 を読んだ受診者は、その日のうちに自己紹介 3 行を作って提案資料に貼れます。Step 3 を読んだ受診者は、スカウトに 5 行で返信できます。Step 6 を読んだ受診者は、既存クライアントへの再提案メールの型を手元に持つことになります。

トーンの書き換えも、要件定義書に修正前 / 修正後の対例を載せました。たとえばこういう書き換えです。

修正前は「皆さんはまず、自分のコンポーネント設計能力を直視すべきです。」です。

修正後は「フロントエンド・バックエンド・データ・モバイルのいずれでも、直近 3 ヶ月で何の意思決定をしたかを 5 つ書き出してみてください。」です。

修正前は CEO の説教、修正後は同じ立場の人からの提案です。

比喩を減らし、職種を問わず通じる言葉に置き換え、断定的な言い回しを「〜してみてください」と弱めていく。要件定義書に書いた 5 つの設計原則を、文面 1 行ごとに当てはめていきました。

Step 1 のメール本文の冒頭は、こうなっています。

```markdown
---
tag: assessment-unified-step1-welcome
subject: 診断結果と、明日からの案件応募で使う3行
preheader: 診断結果から自己紹介3行を作って、今日から提案資料に貼ってください。
---

{{ contact.FIRSTNAME | default: "エンジニア" }} さん

診断、お疲れさまでした。

このメールは、診断結果を「自己理解の到達点」ではなく「明日の案件応募で使う部品」に変えるための 6 通シリーズの 1 通目です。フリーランス白書 2024 によると、フリーランスが案件を取ってきた経路の上位は「人脈・知人紹介」と「過去・現在の取引先からのリピート」でした。新しい客先を開拓するよりも、自分を一文で説明できるほうが、次の紹介につながります。
```

冒頭の宣言で「自己理解の到達点ではない」と明示し、フリーランス白書 2024 の調査結果を引きながら、受診者の課題(紹介から案件が来るしくみ)につなげています。診断結果はその後で、課題に当てはまる部品として登場します。

## 第四部　教訓と、これから

### 9. 4 つの教訓

今回の取り組みから得たものは 4 つあります。

1 つ目は、「人間が判断するだけ」になる状態を作る、ということです。10 分の内訳が「判断」と「目視」だけだったのは、Claude Code(API・コード)と Cowork(ブラウザ・管理画面)の責務境界が事前に決まっていたからです。

境界が曖昧だと、人間が「どっちに振るか」を考える時間が増え、それが 10 分を 30 分に膨らませます。役割分担の設計は、自動化そのものよりも先に固めるべきです。

2 つ目は、自動化をするときに見落とす所、です。前作で自動化を組み上げたとき、満足していました。

しかし、配信されているメールの中身を真面目に読んでいなかった。仕組みが動いたことに満足し、配信物の中身を点検していなかったのです。

自動化を組み終えたからこそ、初めて中身を真面目に見直す余裕が生まれました。自動化は、コンテンツを良くする時間を捻出するための手段です。それ自体が目的になると、間違ったメールを誰よりも効率良く配信することになります。

3 つ目は、コンテンツの IaC 化です。Terraform がインフラの状態を宣言的に管理できるようにしたように、Markdown 正本とビルドパイプラインがメール文面を宣言的に管理できるようにします。

差分が見え、PR でレビューでき、ロールバックできる。HTML を直接編集していた旧構成では、これらが全て難しい状態でした。コンテンツも、コードと同じように扱えます。

4 つ目は、Deep Research の役割です。「説教調を直そう」と直観で書き直すのと、フリーランス白書・HiPro Tech 単価ランキング・Mailchimp ベンチマークを引いた要件定義書に基づいて書き直すのとでは、再現性が違います。

Deep Research は、感覚的な違和感を、データで裏づけられた要件定義書の形に変える役を果たしました。要件定義書が残っているので、半年後に別の人が引き継いでも、同じ判断ができます。

次に挑戦すべきことも見えています。配信時刻の A/B 検証、`ASSESSMENT_TAGS` 単位のさらに細かい差し込み、`CONSENT_DATE` 6 ヶ月超のコンタクト向けの win-back フロー。

要件定義書に書き残した課題が、そのまま次の TODO です。

### 10. 結び ── 自動化が動き始めた日に始まった、本当の仕事

前作の最後の一文はこうでした。「APIの届かない場所を、AIが埋める」。

今回の最後の一文はこうです。自動化が動き始めた日に、本当の仕事が始まる。そして、その本当の仕事も、人間が直接手を動かす時間は 10 分で済みます。

メールファネルというものは、地味な仕事です。アルゴリズムの工夫があるわけでもなく、華やかな技術的挑戦があるわけでもない。

コンタクトリストを作り、属性を定義し、テンプレートを登録し、ワークフローを組み、テスト送信して、配信状況を眺める。今回はそれに加えて、配信されたメールを真面目に読み、自分の書いた説教の数を数え、要件定義書を起こし、文面を書き直し、Brevo を組み直しました。

このうちタイピングを伴う仕事は、ほぼ全て Claude Code か Cowork が担いました。残った仕事は、判断と目視だけです。

「ここだけ手動か」という感覚は、もう、ほとんど残っていません。
