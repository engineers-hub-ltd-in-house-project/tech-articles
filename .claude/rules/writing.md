# 日本語記事の書き方規約

このリポジトリで書く全ての記事原稿(`src/articles/<slug>/index.md`、media 別の出力ファイル、メール文面サンプル等)に適用する。

## 一人称・文体

- 一人称は「わたし」(平仮名)。「私」「僕」「俺」は使わない
- 全文ですます調に統一(「である」体・体言止めは見出し以外で避ける)
- 主語が文脈で自明な場合は「わたし」を省略する。1 段落に「わたし」が 2 回以上出るなら片方は落とす
- 「自分」も多用しない。本当に必要な場面に限る

## 語の一貫性(揺れ防止)

同じ概念には同じ語を使う。混在させない。

| 概念              | 採用する語       | 使わない語                         |
| ----------------- | ---------------- | ---------------------------------- |
| 過去の自記事への参照 | 前作             | 前回 / 前回の記事                  |
| メールの受け取り手 | 受診者           | ユーザ / 読者 / 読み手 / 受信者    |
| 締めの章          | 結び             | まとめ / おわりに / 終わりに       |
| 同列の例示        | など             | 等(混在は避け、片方に統一)         |

新しい記事を書くときは、最初に決めて最後まで通す。修正中に揺れを見つけたら一括置換する。
判定:同じ意味の語が 2 種類以上出てきたら、揺れている。1 つに寄せる。

## 禁止語・禁止表現

### ハイプ語(完全禁止)

- 「完全」(接頭辞も強調用法も):「完全自動化」「完全に整合する」「完全に分離されている」すべて NG
- 「徹底」「決定版」「究極」「網羅的」「〜のすべて」「完全網羅」「最終」も同様
- 引用文中の "fully" / "completely" の和訳も「全体として」「すべての」「全面的に」と開く
- 関連:「完成した」もハイプ寄り(「自動化が完成した日」など)。「組み上がった」「動き始めた」と開く

### 比較表記の「vs」

- 「vs」「VS」「vs.」「ｖｓ」を使わない
- 代わりに「Aと比べてB」「Aに対するB」「A・B 比較」「旧 / 新」など日本語で書く

### 警告比喩

- 「罠」「落とし穴」「陥穽」「地雷」「わな」を本文・見出し・要約のいずれにも使わない
- 「自動化の罠」→「自動化をするときに見落とす所」
- 「キラー機能」「銀の弾丸」「魔法のような」など誇大な英語比喩の和訳も避ける

### 詩的・難解な比喩

- 「覆い隠す傘」「context を燃やす」「水質を点検する」のような詩的・直訳比喩を避け、文字通りの説明的な日本語に開く
- 「原典の温度のまま読む」→「原典で確認する」
- 「思想として地続き」「同じ方角を向く」→「同じ系列の話」「整合する」
- 「踏み込む」(発言の度合)→「述べる」
- 例外:「telephone game」「signal/noise」「context window」など原語のまま定着しているメタファーはセーフ
- 判定軸:小説じゃない。声に出して読んだとき、読み手が一度立ち止まる比喩は捨てる

### 自社プロダクト名

- 公開記事の本文・体験談で MyBO / engram / Recoro 等の自社プロダクト名は使わない
- 抽象化する例:「ある SaaS の運用案件で」「ある適性診断 SaaS」「弊社のとあるサービス」
- OS / 言語 / インフラの一般固有名(muClibc、BusyBox、Solaris 8、LDAP、sh、Zabbix、Brevo、Linear 等)は使ってよい
- 判断軸:自社が販売・提供しているプロダクトかどうか

## 漢字熟語・漢語の凝縮

### 辞書にない四字熟語を作らない

- 「性能装置」「速度装置」「圧縮装置」(performance machine 等の直訳)NG
- 「コンテキスト超過対応」→「コンテキストの超過に対する対応」
- 「最終確定」→「確定」
- 「人手起動」→「人が起動する」/「明示起動」→「明示的に起動する」
- 「人間時間」→「人が手を動かす時間」「人が触る時間」(2026-05-02 発生例)
- 「会話応答」→「会話への応答」/「進捗報告」→「進捗の報告」
- 「装置」「機構」「線」など大和言葉でも、抽象的に使うなら「物」「道具」「仕組み」「構造」と開く

### 辞書にある漢語でも 2〜3 段重ねたら開く

- 「自己理解の深化に終始」→「自己の理解を深めることに集中」
- 「案件獲得の実務に翻訳」→「実際に案件を取る場面で活かす」
- 「集中配置」→「集中して置く」
- 「ID 採番」→「ID を割り振る」
- 「単価交渉の根拠 3 点構造化」→「単価交渉の根拠を 3 点に整理」
- 「面談 5 大質問への回答整理」→「面談でよく訊かれる 5 つの質問への答えを揃える」
- 「即貼付」→「そのまま貼れる」
- 「紹介の連鎖を生む」→「次の紹介につながる」
- 「課題に接続する」→「課題につなげる」
- 「課題への翻訳として診断結果を用いる」→「課題に当てはまる形で診断結果を示す」
- 「引き継ぎ可能性」→「引き継ぎやすさ」
- 「影響を考慮し」→「影響を踏まえ」
- 「即見直し」→「すぐ見直す」
- 「管理可能にする」→「管理できるようにする」
- 「変換する仕組み」→「変える役を果たす」「変える働き」
- 例外:技術用語として定着している複合語(「コンテキストエンジニアリング」「責務分担」「依存関係」「設定ファイル」「バッチ処理」)は開かなくてよい
- 判定軸:声に出して読んで漢語の重なりで一度息が止まったら、開く

### 不要な「〜的に」を削る

- 「乗算的に劣化」→「乗算で落ちる」
- 「指数関数的に増える」→「指数で増える」「倍々に増える」
- 「線形的に伸びる」→「比例して伸びる」
- 「構造的に派生」→「構造として生まれる」
- 例外:「自律的に」「動的に」「明示的に」「自動的に」「端的に」「宣言的に」は技術文脈で定着しているのでセーフ
- 判定軸:対応する自然な日本語が一発で思いつくならそちらを使う

## 不自然なカタカナ英語・横文字を控える

対応する自然な日本語があるのに、カタカナ語・英単語をそのまま使わない。

- 「ピア・ツー・ピア」→「同じ立場の人として」「対等な相手として」
- 「Before / After」→「修正前 / 修正後」「対応前 / 対応後」
- 「Hook(冒頭の)」→「冒頭のつかみ」
- 「Next Action」→「次の一手」「次にしてほしい行動」
- 「CTA」→「行動喚起」(または文脈に合う日本語)
- 「welcome flow」→「登録直後のメール」「登録直後の流れ」
- 「canary」→「目安」「監視のサイン」
- 「deliverability」→「到達率」
- 「unsubscribe rate」→「配信解除率」
- 「ミュートする」(メール文脈)→「配信解除する」
- 「前重心の配信」「高重心」のような訳語っぽい造語も避ける。「前半に集中させた配信」「最初の 1 週間に集中させる配信」と開く
- 例外:技術用語として原語が定着しているもの(API、HTML、Markdown、KPI、CTR、CTOR、IaC、TODO、A/B 検証、Terraform、Brevo、Linear、Slack 等)はそのまま使う
- 判断軸:声に出して読んだとき、横文字を 1 度頭の中で日本語に翻訳していたら、そもそも日本語で書く

## Markdown 記法

### 太字を使わない

- 本文中で `**text**` の Markdown 太字を強調目的で使わない
- 強調したい場合は、その文を独立した短い段落に切り出すか、見出しに昇格させる
- 例外:見出し記法 `#` は太字相当だが、太字としては扱わない
- リスト項目の頭の用語ラベル `- **用語**: 説明` も控えめに。説明調で書けるなら平文に開く

### 鉤括弧を必要以上に使わない

- 「A」「B」「C」のように 3 個以上連ねる場面では Markdown の箇条書きに展開する
- 箇条書きに展開したら各項目から `「」` を外す:NG `- 「コンポーネント」` / OK `- コンポーネント`
- 対応関係(A → B)も両側から外す: `- A → B`
- インライン引用「1 つ目は『〜』です」のような枠で囲む書き方も避ける。「1 つ目は、〜という考え方です」のように地の文に溶かす
- 2 個までは平文のまま「A」「B」で構わない
- 例外:項目に句点・空白・記号が含まれて区切りが曖昧になるとき、または項目自体が文単位の長い引用のとき

### 列挙の数詞

- 「ひとつ。ふたつ。みっつ。」のような大和言葉ではなく、`1.` `2.` `3.` または「1 つ目」「2 つ目」「3 つ目」を使う

### 段落のサイズ

- 1 段落(空行で区切られたブロック)は note / Zenn のプレビューで 3 行前後に収める。原稿の文字数では概ね 100 字以内が目安
- 文数の上限は 3 文。4 文以上は無条件で分割する
- 長文(おおよそ 40 字以上)が 2 文連続したら、その時点で 1 段落とみなして次の文の直前で切る
- 主題が切り替わる地点(全体像 → 内訳、定義 → 例示、現状 → 転換、過去 → 現在)では、その直前で必ず切る
- 「しかし」「一方」「ここで」「結果として」「今回扱うのは」のような接続詞・転換句の直前は、ほぼ常に切れ目になる
- 短文(各 30 字未満)の連続は 2〜3 文を 1 段落にまとめてよい
- リスト・コードブロック・テーブルの直前直後は自然に空行が入るので、追加分割は不要

判定:書いた段落を声に出して読み返したとき、息継ぎが 1 回で足りなければ切る。note のプレビューで 4 行以上になっていたら必ず割る。

## 引用・出典

- 引用は `>` ブロック引用で原文を残し、その下に和訳と短い解説を続ける
- URL は信頼できる場所(公式ドキュメント、論文 arXiv 等)のみ。手元になければ「(出典確認中)」と書き、推測 URL は書かない
- 一次資料は末尾の `## 参考・関連リンク` に列挙する

## 自己点検

記事を書き上げたら、ビルド前に以下を grep で確認する。

```bash
grep -nE '私[^自的鉄信]|完全|完成|徹底|決定版|究極|網羅|罠|落とし穴|engram|MyBO|Recoro| vs |vs\.' src/articles/<slug>/index.md
grep -n '\*\*' src/articles/<slug>/index.md
grep -nE '人間時間|集中配置|採番|前重心|高重心' src/articles/<slug>/index.md
grep -nE 'Before|After|Hook|Next Action|welcome flow|canary|deliverability|unsubscribe' src/articles/<slug>/index.md
grep -nE '前回の記事|読み手|読者|ユーザ|受信者' src/articles/<slug>/index.md
```

ヒットがあれば、本ファイルの該当規約に従って書き直す。
